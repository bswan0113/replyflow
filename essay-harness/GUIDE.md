# 에세이 작성 가이드

블로그용 짧은 에세이 한 편을 끝까지 완성하기 위한 가벼운 진행 가이드다.
클로드 코드, Codex 등 어떤 에이전트를 쓰든 이 문서를 읽고 그대로 따르면 된다 —
특정 툴의 기능(서브에이전트 자동 호출, 스킬 시스템 등)에 의존하지 않는다.

무거운 상태머신이나 changelog, 단계별 자동 검증 게이트는 쓰지 않는다.
매 단계는 그냥 사용자와의 대화이고, 다음 단계로 넘어갈지는 사용자가 결정한다.

## 저장 위치

에세이 한 편 = `essays/<slug>.md` 파일 하나. 파일 맨 위에 아래 frontmatter만 유지한다.

```yaml
---
title: 가제
status: idea # idea -> draft -> post -> ready
---
```

`status`가 그 에세이의 유일한 진행 상태 표시다.

발행 기록은 `essays/_log.md` 파일 하나가 전담한다 (형식은 아래 3단계 참고).
그 외 별도의 상태 파일, 서브에이전트, changelog는 없다.

## 진행 방식

에세이 작업을 시작하면, 대상 파일이 있는지 먼저 확인한다.

- 파일이 없으면 → **소재구상**부터 시작.
- 파일이 있으면 → frontmatter의 `status`를 보고 해당 단계부터 이어간다.

각 단계의 산출물은 그 에세이 파일에 직접 반영한다. 단계를 건너뛰거나 되돌아가는 것도 자유롭다 — 강제되는 순서는 없다.

### 1. 소재구상 (status: idea)

목표: 무엇에 대해, 누구에게, 어떤 한 가지 요점을 전달할지 정하고, 예전에 이미 쓴 소재는 아닌지 확인한다.

**아이디어가 없는 경우**: 사용자의 관심사나 최근 대화에서 실마리를 잡아 토픽 후보를 몇 개 제안한다. 사용자가 하나를 승낙하면 다음으로.

**아이디어가 있는 경우**: 정해진 형식 없이 그 토픽에 대해 자유롭게 대화한다. 사용자가 "이 내용으로 써줘"라고 명시적으로 말할 때까지는 집필로 넘어가지 않는다.

**중복 확인**: 토픽이 사실상 확정되는 시점에, `essays/_log.md`를 훑어서 같은 소재를 이미 쓴 적이 있는지만 확인한다 (웹 검색 불필요 — 이 로그 파일이 유일한 판단 근거). 겹치는 게 있으면 사용자에게 알리고, 그래도 진행할지 / 각도를 다르게 할지 물어본다.

확정되면 파일에 `## 기획` 섹션으로 주제, 핵심 요점(한 문장), 예상 독자를 정리하고 `status: draft`로 바꾼다.

### 2. 집필 (status: draft)

목표: 처음부터 끝까지 읽히는, 품질 좋은 완성 초안 한 편.

**형식**: 마크다운 파일로 작성한다. 이미지 삽입은 필수가 아니지만, 가독성과 흥미를 위해 넣으면 좋을 위치가 있다면 "여기에는 이런 이미지가 어울린다"는 제안을 해준다 (실제 이미지 생성은 하지 않는다).

**품질을 끌어올리는 방법**: 초안을 쓰거나 다듬을 때 아래 관점을 적용한다.
- 도입부 첫 문장에서 바로 흥미를 끈다 (배경 설명으로 늘어지지 않는다).
- 글 전체가 하나의 핵심 메시지를 향하게 한다 — 곁가지 주장은 쳐낸다.
- 추상적인 주장 뒤에는 구체적인 사례·디테일·숫자를 붙인다.
- 문장 길이에 리듬을 준다 (짧은 문장과 긴 문장을 섞는다).
- 상투적 표현, 군더더기 수식어를 덜어낸다.
- 마지막 문단은 요약으로 끝내지 않고, 여운이나 한 번 더 생각하게 만드는 지점으로 끝낸다.

**온디맨드 평가**: 사용자가 "평가해줘" 등으로 요청하면, 지금까지 이 글을 써온 대화 맥락을 배제하고 초안 텍스트만 처음 읽는 것처럼 아래 세 기준으로 평가한다. (가능한 환경이면 별도 서브에이전트나 새 세션을 띄워 실제로 작성 맥락 없이 읽게 한다. 그런 기능이 없으면, 최소한 "왜 이렇게 썼는지"를 잠시 제쳐두고 낯선 독자의 눈으로 다시 읽는다.)

1. 문장/글 품질 — 리듬, 명료성, 군더더기, 상투어, 도입부와 마무리의 힘
2. 구체적 개선 지점 — 어디를 왜 어떻게 고치면 나아지는지 ("좋다/별로다" 같은 막연한 평가 금지)
3. 담론/논지 수준 — 주장이 진부하지 않은지, 논리가 탄탄한지, 독창적인 시각이 있는지

평가 결과는 사용자에게 그대로 보여주고, 반영 여부와 방식은 사용자와 상의해서 정한다 — 자동으로 고쳐 쓰지 않는다. 몇 번이든 다시 요청할 수 있고, 정해진 횟수 제한은 없다.

이 단계 안에서 퇴고까지 함께 다룬다 — 별도 단계로 나누지 않고, 사용자와 여러 번 주고받으며 다듬는다. 요청받지 않은 톤·구조 변경은 임의로 하지 않는다.

초안을 `## 초안` 섹션에 적고, 사용자가 만족하면 `status: post`로 바꾼다.

### 3. 후작업 (status: post)

목표: 분류하고 기록을 남긴다.

- 카테고리 후보를 제안한다.
- 태그 후보를 제안한다.
- 이 글이 기존 글과 시리즈로 묶일 만하면 한 줄로 제안한다 (구조화된 시리즈 관리 체계는 만들지 않는다 — 그냥 언급 수준).
- `essays/_log.md`에 한 줄을 추가한다: 날짜, 제목, 토픽/카테고리, 태그, (있으면) 시리즈 한 줄.

**로그는 이 단계를 완료할 때만 기록한다.** 초안 상태에서 중단된 글은 로그에 남기지 않는다 — 그래야 나중에 소재구상 단계의 중복 확인이 죽은 초안 때문에 오탐하지 않는다.

완료되면 `status: ready`로 바꾼다.

### 4. 게시 (status: ready)

목표: 그대로 복사해서 올릴 수 있는 상태로 마무리한다.

- 제목 후보 2~3개를 제안한다.
- 원하면 한두 문장짜리 요약/메타 설명을 만들어준다.
- 오탈자, 마크다운 서식 등 플랫폼 무관 정리를 확인한다.
- 특정 플랫폼(브런치, 티스토리, 미디엄 등)에 맞춘 서식 조정이 필요하면 물어보고 반영한다.

여기서 하네스의 역할은 끝난다. 실제 게시는 사용자가 직접 한다 — 별도의 발행 자동화는 없다.

## 하지 않는 것

- 여러 에세이를 오케스트레이션하는 상위 상태 파일 (`project.yaml` 류) 없음.
- 단계마다 서브에이전트를 자동으로 호출하지 않음 — 전부 메인 대화에서 처리.
- changelog나 버전 이력 파일을 따로 두지 않음. 필요하면 git 커밋 이력이 그 역할을 한다.
- 태그·카테고리·시리즈를 로그에 구조화된 필드/DB로 관리하지 않음 — 한 줄 기록과 한 줄 제안 수준만 유지한다.
- 단계 통과를 판정하는 별도 "리뷰어" 절차 없음 — 다음 단계로 넘어갈지는 사용자와의 대화로 결정한다.
